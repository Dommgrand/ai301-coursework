# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| silent drift | Compare the changed files and behavior in the unified diff with the plan's stated scope, expected behavior, and documented deviation notes. Compare the draft PR title and description with the actual diff and relevant issue requirements. | The change stays within the plan and its documented deviations, and the PR description accurately represents the substantive behavior implemented. Distinguish the promised behavior from illustrative examples of output: a wording or formatting difference in an example is not by itself a material contradiction when the diff supports the stated behavior. Fail when the diff materially contradicts a promised behavior, silently expands or misses the agreed scope, or leaves an important behavioral discrepancy unexplained. Do not excuse a missing requirement merely because the PR discloses it. | required |
| not tested | Compare the test-evidence section with the plan's test plan, the relevant reproduction steps, and the repository's own required checks. Inspect actual commands, outputs, before/after results, and any stated failures or limitations. | The evidence establishes the important validation outcomes through relevant test results, reproduction evidence, or other concrete support. Evaluate whether the evidence supports the substantive behavior claimed, rather than requiring every illustrative output string to match exactly. A concise test report may support a claim when it is consistent with the other evidence, but a bare claim must not override contradictory evidence. Missing validation, known failures, and limitations must be disclosed with their implications. Fail when a material behavior is unverified, evidence contradicts a claimed result, or required validation is silently omitted. | required |
| unreviewable | Inspect the unified diff and changed-file list against the plan's boundary. Look for unrelated edits, generated artifacts, debug leftovers, dead or commented-out code, accidental files, and formatting churn that obscures the intended change. | The intended change can be reviewed in context, and unrelated material does not obscure or materially complicate evaluating it. Incidental changes are acceptable when justified by the plan or a documented dependency. Fail when unrelated or leftover material makes it materially difficult to identify and assess the actual fix. Do not fail solely because a diff is long or contains multiple files. | required |
| standards wall | Inspect the repository-facts block for the PR template's required sections, contribution instructions, relevant maintainer direction, and applicable disclosure or AI-use policy. Compare those requirements with the draft title and description and any required checklist or disclosure fields. | Every applicable required template field, contribution requirement, maintainer instruction, and AI-use disclosure is completed truthfully. A requirement that does not apply is identified as not applicable where needed. Fail when a required field or disclosure is missing, misleading, or contradicted by the available evidence. Do not invent repository rules that are not present in the evidence. | required |

## Verdict rule

Return `accept` only when every required check passes. Return `reject` if any required check fails or remains unclear because the evidence cannot establish that its pass condition is met. Treat `unclear` as a failure for verdict purposes. Preferred checks, if added later, never change the verdict.

Apply the honest-outcome rule across all checks: a documented limitation or deviation is not automatically a rejection. Evaluate whether it is accurately disclosed, supported by evidence, and compatible with the repository's stated requirements. Do not treat disclosure as a substitute for a requirement that explicitly must be satisfied before submission.
